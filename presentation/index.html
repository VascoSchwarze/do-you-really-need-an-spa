Warum wurden SPAs zum Standard?

  • flüssigere UX
  • Nutzung von Hardware-Fortschritten
  • geringere Serverlast
  • Komponentenwiederverwendung
  • riesiges Ökosystem
  • Team-Gewohnheit
  • SPAs sind keine reine Modeerscheinung
  • flüssige, schnelle, responsive Navigation, App-ähnliches Gefühl
  • bessere Hardware in Endgeräten kann mehr Code selber ausführen
  • Rendering auf Client-Seite -> geringere Serverlast, weniger Netzwerkanfragen
  • Komponentenwiederverwendung: echter Fortschritt (gekapselte UI-Bausteine statt große HTML-Templates), klares mentales Modell
  • außerdem: klare Trennung von Frontend und Backend (einfachere Cross-Platform/mobile Anwendungen)
  • React/Vue/Angular-Ökosystem: ausgereiftes Tooling, riesige Community
  • nach Etablierung: Team-Gewohnheit: Weg des geringsten Widerstands, unabhängig von technischer Eignung
  • Historischer Verlauf: von SSR (PHP/JSP/Rails) über jQuery zu Backbone/Angular/React-CSR — Fortschritt für hochinteraktive Apps, aber wurde Standard auch für reine Content-Seiten

Die technischen Kosten

  • JS benötigt
  • Größere Bundles
  • Verzögertes Laden der Seite
  • schwieriges SEO
  • Accessibility-Einschränkungen
  • ohne JS geht gar nichts
  • Bundlegröße skaliert schlecht, bspw, wenn ich neue Dependencies/Funktionalitäten auf einer Seite hinzufüge, wird dies immer mit geladen, auch wenn ich nur eine andere Seite sehen will
  • Reines CSR: Server liefert nur leeres HTML-Grundgerüst, sichtbarer Inhalt erst nach Download, Parsen und Ausführen des JS-Bundles (sequentiell) (auf schwachen Mobilgeräten besonders kritisch)
  • SEO
    • Google und zunehmend auch andere Suchmaschinen können SPAs crawlen/indexieren über zusätzlichen, Rendering-Schritt, klappt mittlerweise fast genauso gut wie MPAs
    • ABER: nicht jeder Bot rendert JS: Social-Preview-Bots (Slack, X, LinkedIn), Legacy-Tools sehen nur initiales HTML, welches leer ist
    • UND: einzelne Seiten können bei SPA nicht oder nur schwer unabhängig voneinander gerankt werden, aktualisierter Inhalt wird langsamer entdeckt/re-indexiert
    • Für Content-/Marketing-Seiten mit SEO-Relevanz: konkretes Risiko der SPA-Architektur
  • Accessibility
    • Screenreader erkennen Seitenwechsel in SPAs oft nicht automatisch
    • Bestimmte Browser-integrierte Funktionen wie Formulare oder Historie müssen in SPAs oft nachgebaut und verwaltet werden

Lässt sich das messen?

  • Core Web Vitals
    • LCP   < 2,5sek
    • INP   < 200ms
    • CLS   < 0,1
  • TTI
  • FCP
  • Core Web Vitals = Google-definierte UX-Metriken, fließen in Suchranking ein (SEO)
  • LCP (Largest Contentful Paint): Ladezeitpunkt des größten Content-Element — bei CSR-SPAs abhängig von Bundle-Laden/Parsen/Ausführen + Datenladen, jede Stufe addiert sich (sollte unter 2,5 sek sein)
  • INP (Interaction to Next Paint): Reaktionsgeschwindigkeit auf Klicks/Eingaben — leidet bei blockiertem Hauptthread (sollte unter 200ms sein)
  • CLS (Cumulative Layout Shift): visuelle Stabilität, verschieben sich Elemente nach dem ersten Render? (sollte unter 0,1 sein)
  • Alle 3 Metriken: nicht nur UX-, sondern auch Business-relevant (SEO-Ranking)
  • TTI: nicht standardisiert, aber ehrlicher UX-Wert — wann Seite zuverlässig auf Eingaben reagiert (Event-Handler registriert, Hauptthread frei, keine Netzwerkaktivität)
  • FCP: wann erster Inhalt gerendert wird — bei SPA trügerisch früh, falls nur Spinner/leeres Grundgerüst
  • Bei SPA liegt TTI oft deutlich nach FCP (Lücke zwischen "sichtbar" und "vollständig hydriert")

Astros Philosophie

Ship Zero JavaScript by Default
  • Jede Astro-Komponente wird zu Build-/Request-Zeit zu statischem HTML/CSS gerendert, das dafür nötige JS wird verworfen
  • Umkehrung der SPA-Grundannahme: SPA = "alles braucht JS, bis Gegenteil bewiesen"; Astro = "nichts braucht JS, bis explizit als interaktiv markiert"
  • Dieser Perspektivwechsel ist der Kern der Islands Architecture (Details folgen)

Islands Architecture

Header (interaktive Insel)
Sidebar (statisch)
Hauptinhalt (statischer Text, Bilder etc.)
Karussell (interaktive Insel)
Footer (statisch)
  • JS wird nur für Inseln geladen
  • Laden inital zusammen mit dem Rest der Seite, oder auch erst, wenn das Element sichtbar wird

Anatomie einer .astro-Datei
  • .astro-Syntax ist Übermenge (engl. superset) von HTML, reines HTML ist gültige Astro-Komponente

Anatomie einer .astro-Datei
  • .astro-Datei hat zwei Zonen: "Frontmatter" oben zwischen drei Bindestrichen (enthält JS oder sogar TS), darunter das Template (HTML-artiges Markup)
  • Frontmatter: Ganz normales TypeScript: Imports, Typen, Props

Anatomie einer .astro-Datei
  • Inhalt von Frontmatter wird zur Build-Zeit ausgeführt (nie im Browser), es entsteht statisches HTML
  • Templatesyntax: Sieht aus wie JSX: {} betten JS-Ausdrücke ein, .map() für Listen funktioniert identisch
  • Kleine, aber angenehme Unterschiede zu JSX: normales class statt className, kein key-Prop bei Listen nötig
  • Kein umschließendes Fragment (<>...</>) nötig — ein Astro-Template darf mehrere Root-Elemente nebeneinander haben
  • Bedingtes Rendern wie in JSX: {condition && <div>...</div>}

Einordnung

  • Qwik  -  Resumability
  • htmx  -  HTML-Attribute statt Komponenten
  • Next.js  -  Partial Prerendering / RSC
  • Astro  -  unser Beispiel heute
  • Einordnung für Kenner/Skeptiker ("ist das ein Astro-Werbe-Talk?"): Astro ist nicht die einzige/erste Umsetzung dieser Idee
  • Qwik: "Resumability" — serialisiert State ins HTML, setzt Ausführung im Client fort, ganz ohne Hydration-Schritt

  • Next.js: Partial Prerendering / React Server Components — Server Components laufen nur serverseitig, nie client-seitiges JS
  • Astro als zugängliches Beispiel für größeres Denkmuster gewählt — nicht die einzig richtige Antwort

Such-/Filterleiste — Logik

examples/recipe-astro/src/scripts/search-filter.ts
function applyFilter() {
  const query = input.value.trim().toLowerCase();
  let visibleCount = 0;
  for (const card of cards) {
    const matchesQuery = query === "" || card.dataset.title!.toLowerCase().includes(query);
    const matchesCategory = activeCategory === "" || card.dataset.category === activeCategory;
    const visible = matchesQuery && matchesCategory;
    card.hidden = !visible;
    if (visible) visibleCount++;
  }
  countEl.textContent = `${visibleCount} ...`;
}

input.addEventListener("input", applyFilter);

Sofort aktiv — kein Hydration-Delay nötig

  • Vollständige Kernlogik: kein virtueller DOM, direkte DOM-Manipulation (card.hidden = !visible) statt Neu-Rendern
  • Skript liest Karten direkt aus DOM (data-title, data-category)
  • Kein Framework-Komponentenmodell → keine Hydration-Timing-Direktiven wie client:load nötig; normales <script>-Tag reicht (Astro bündelt automatisch pro Seite)
  • Punkt bleibt: sofort verfügbar — es gibt schlicht nichts zu "hydrieren"

Portionsrechner

examples/recipe-astro/src/scripts/portion-calculator.ts
function scaleAmount(amount: number, baseServings: number, targetServings: number): string {
  const scaled = (amount * targetServings) / baseServings;
  const rounded = Math.round(scaled * 100) / 100;
  if (Number.isInteger(rounded)) return String(rounded);
  return rounded.toFixed(rounded < 10 ? 2 : 1).replace(/\.?0+$/, "");
}

// ... render() aktualisiert Input + alle .amount-Elemente
decrement?.addEventListener("click", () => render(Math.max(1, currentServings() - 1)));
increment?.addEventListener("click", () => render(currentServings() + 1));

Weiter unten auf der Seite — trotzdem sofort aktiv

  • Skaliert Zutatenmengen live bei Änderung der Portionsanzahl — reine Mathematik + DOM-Updates, kein Framework
  • scaleAmount rundet sinnvoll; Basismenge/-portionen kommen als data-*-Attribute vom Server, Skript liest nur aus
  • Ursprünglich client:visible (Intersection Observer) geplant, da Rechner weiter unten sitzt
  • Entfällt bei Vanilla-JS: kein Framework-Runtime-Overhead pro Insel → kein Kostenvorteil durch verzögerte Aktivierung, Skript läuft immer sofort
  • Merke: bei echten Framework-Islands (Preact/React/Vue) wäre client:visible weiterhin sinnvoll

Favoriten-Toggle

examples/recipe-astro/src/scripts/favorite-toggle.ts
function initFavoriteToggle(button: HTMLButtonElement) {
  const slug = button.dataset.slug;
  const sync = () => {
    const active = readFavorites().has(slug);
    button.textContent = active ? '♥' : '♡';
    button.classList.toggle('is-active', active);
  };
  button.addEventListener('click', () => {
    const favorites = readFavorites();
    favorites.has(slug) ? favorites.delete(slug) : favorites.add(slug);
    writeFavorites(favorites);
    sync();
  });
  sync();
}
  • Liest/schreibt direkt in localStorage — kein globales State-Management (Context/Redux) nötig
  • Jede Button-Instanz synchronisiert unabhängig ihren Zustand (sync()); mehrere Instanzen möglich, komplett unabhängig voneinander
  • Vergleich zu React: dort zentraler Hook (useFavorites/useSyncExternalStore) als Single Source of Truth nötig
  • Bei Astro-Islands nicht nötig: localStorage selbst ist die Source of Truth, kein geteilter In-Memory-State

Design-Entscheidung: Warum kein Framework für die Islands?

Was viele Tutorials tun

React als Standard-Insel — mehr JS als nötig

Was hier gemacht wurde

Vanilla-JS — 0 KB Framework-Runtime

Für "Checkbox abhaken" muss man kein 40-KB-Framework mit der Kettensäge auspacken.

  • Wird in vielen Tutorials übergangen: Astro unterstützt React/Vue/Svelte/Solid/Preact als Islands, Tutorials greifen reflexartig zu React
  • Widerspricht Astros Kernidee: jede React-Insel bringt React+ReactDOM-Runtime mit (~40+ KB gzipped), egal wie simpel die Interaktion; Preact (~4 KB) wäre schon besser
  • Hier noch weiter gegangen: für alle vier Features keine Component-Hydration/virtueller DOM nötig — reine DOM-Manipulation via addEventListener
  • Ergebnis: 0 KB Framework-Runtime für die gesamte App
  • Echte Abwägung im Projekt: Bundle-Größe vs. Team-Vertrautheit/Entwicklungsgeschwindigkeit — bei komplexeren Features (z. B. Formulare) kann React-Insel pragmatischer sein
  • Punkt: nicht "Vanilla ist immer richtig", sondern bewusste Abwägung statt Reflex — dieselbe Frage wie im gesamten Talk

Content Collections: typisierte Daten

examples/recipe-astro/src/content.config.ts
const recipes = defineCollection({
  loader: glob({ pattern: "**/*.yaml", base: "./src/content/recipes" }),
  schema: z.object({
    title: z.object({ de: z.string(), en: z.string() }),
    category: z.enum(["Vegetarisch", "Fleisch", "Dessert", "Vegan"]),
    cookTime: z.number().positive(),
    difficulty: z.number().int().min(1).max(5),
    servings: z.number().int().positive(),
    ingredients: z.array(z.object({
      name: z.string(), amount: z.number().positive(), unit: z.string(),
    })),
    // ...
  }),
});
  • Astros eingebautes System für typisierte, strukturierte Inhalte
  • Hinweis: ursprünglich Markdown/Frontmatter geplant, tatsächlich YAML gewählt (rein strukturierte Daten ohne Fließtext) — Prinzip identisch
  • loader (glob) liest Dateien ein, Zod-Schema definiert Felder/Typen inkl. verschachtelter Objekte, Enums, Validierungsregeln
  • Vorteil ggü. SPA (loses JSON ohne Validierung): Build-Zeit-Garantie fürs Format + volle TypeScript-Typinferenz über getCollection()

Tippfehler in category → Build schlägt fehl, nicht Laufzeit

Der Compiler flext jetzt mit Rechtschreibprüfung.

  • Gedankenspiel: Tippfehler category: "Desert" statt "Dessert" (Schema erlaubt nur 4 feste Werte)
  • Bei klassischem JSON ohne Validierung (React-Baseline): Fehler fällt erst zur Laufzeit auf (leere Übersetzung/"undefined"), evtl. erst wenn Nutzer sich beschwert
  • Mit Zod-Schema in Astro: Build schlägt fehl mit klarer Fehlermeldung (Feld + Datei)
  • "Shift left"-Prinzip: Fehler von Laufzeit (beim Kunden) zu Build-Zeit (beim Entwickler) verschoben

Server rendert wieder HTML zur Laufzeit? Herzlichen Glückwunsch, wir haben PHP neu erfunden. 🐘

Image Optimization: <Image />

[[Platzhalter — Beispielprojekt ergänzen]]
  • Automatische Formatkonvertierung (z. B. WebP/AVIF)
  • Automatische Größenanpassung je Anzeigekontext
  • Direkter Effekt auf LCP, da Bilder oft das größte Content-Element sind
  • <Image /> (aus astro:assets) optimiert Bilder beim Build: WebP/AVIF-Konvertierung, passende Größenvarianten, automatische width/height gegen Layout-Shifts
  • Effekt auf LCP: größtes Content-Element ist oft ein Bild — kleinere/komprimierte Datei wirkt sich direkt auf LCP aus

Server Islands: server:defer

[[Platzhalter — Beispielprojekt ergänzen]]

Serverseitig gerendert, verzögert nachgeladen

Reale Use Cases für SSR / Server Islands

  • Authentifizierung & personalisierte Inhalte
  • CAPTCHAs
  • Häufig wechselnde, nicht vorab bekannte Daten
  • Allgemeines Konzeptwissen, unabhängig vom fehlenden Beispielcode
  • Reale Gründe für SSR/Server Islands: Auth (personalisierte Inhalte), CAPTCHAs (müssen serverseitig validiert werden), zu häufig/individuell wechselnde Inhalte (Dashboard, Warenkorb, Live-Preise)
  • Wichtige Botschaft: Wechsel zu "gezielt dynamisch" nur für die Teile, die es brauchen — nicht die ganze App
  • Vorteil ggü. "alles ist SPA": inkrementell genau so viel Dynamik hinzufügen wie nötig

Ökosystem: Deployment-Adapter

  • Node.js (eigener Server)
  • Vercel, Netlify, Cloudflare (Edge/Serverless)
  • Adapter kapseln die Plattform-spezifische Integration
  • Astro bietet offizielle Adapter für gängige Plattformen: Node.js-Server, Vercel, Netlify, Cloudflare Pages/Workers
  • Adapter übernimmt plattformspezifische Integration (Request-Handling, Response-Streaming)
  • Anwendungscode bleibt plattformunabhängig — Deployment-Ziel wechselbar ohne Code-Anpassung

Wann SPAs weiterhin die bessere Wahl sind

  • Komplexe, hochinteraktive Anwendungen mit viel Client-State
  • Dashboards, Editoren, Tools mit dauerhaftem "App-Charakter"
  • Content-Charakter: Ausnahme, nicht Regel
  • Astro und MPAs generell sind kein Wundermittel
  • Basierend auf den 4 Fragen: SPAs bleiben beste Wahl für komplexe, hochinteraktive Apps mit viel geteiltem Client-State (Dashboards, Editoren, PM-Tools) — "App-Charakter" statt "Content-Charakter"
  • Keine Ausnahme von der Kernthese, sondern logische Konsequenz: bei Figma/Linear-artigen Tools ist "sehr viel JS" die ehrliche Antwort → SPA ist dann konsequent richtig, keine schlechte Gewohnheit

Ein Fragenkatalog

Wie viel der Seite ist tatsächlich interaktiv gegenüber reinem Content?

  • expliziter Fragenkatalog für jede Framework-Wahl, unabhängig vom Ergebnis
  • Grundlegendste Frage: Marketing-Seite/Blog/Doku/Rezepte-App = überwiegend reiner Content → spricht für Islands-/Content-first-Ansatz
  • Grafik-Editor/PM-Board/Dashboard = fast alles interaktiv → klassische SPA passt besser

Frage 2

Wird clientseitiger Zustand benötigt, der über viele Komponenten hinweg geteilt und synchron gehalten werden muss?

  • Anknüpfung an Favoriten-Toggle-Vergleich: braucht es geteilten, synchronen State über mehrere UI-Bereiche (z. B. Warenkorb-Icon, Formular mit Cross-Feld-Validierung)?
  • Islands sind bewusst isoliert — Stärke bei einfachen lokalen Interaktionen, Schwäche bei viel geteiltem State
  • Lösbar auch mit Islands (Astro empfiehlt Nanostores), aber ab gewissem Komplexitätsgrad ist SPA mit eingebautem State-Management oft pragmatischer

Frage 3

Ist SEO bzw. Time-to-First-Content ein kritischer Faktor für das Projekt?

  • Öffentliche Inhalte (Marketing, Blog, Produktseiten, Doku): fast immer "ja" → spricht für Content-first-Ansatz
  • Interne Tools/Admin/Login-geschützt: SEO irrelevant → Argument entfällt, andere Kriterien entscheiden

Frage 4

Besteht bereits eine erhebliche Investition in ein bestehendes SPA-Setup?

  • Pragmatische Frage, geht in technischen Diskussionen oft unter: Team-Know-how, gewachsene Codebasis, Tooling-Integrationen haben realen Wert/Umstellungskosten
  • Technisch "besseres" Paradigma rechtfertigt nicht automatisch Neuentwicklung
  • Abwägung: junges Projekt + starke Antworten auf Fragen 1-3 → Architektur-Vorteil überwiegt; etabliertes Produkt/eingespieltes Team → oft anders

Take-away 1

Die entscheidende Frage ist nicht "Welches Framework?", sondern "Wie viel JavaScript braucht diese Seite tatsächlich?"

— unabhängig davon, ob am Ende Astro, Qwik oder etwas anderes zum Einsatz kommt.

  • Wichtigster, framework-unabhängiger Take-away — betont und langsam vortragen
  • Kernbotschaft ist NICHT "benutzt Astro", sondern: erst Interaktivitätsbedarf klären, dann Framework wählen
  • Framework-Wahl ist die Antwort auf die Frage, nicht der Ausgangspunkt

Take-aways 2 & 3

  • Islands Architecture: partielle Interaktivität
  • Fragenkatalog: Werkzeug für die nächste Entscheidung
  • Take-away 2: Islands Architecture ist ein Denk-Muster, kein Astro-exklusives Feature — als Bewertungsraster unabhängig vom Tool nutzbar
  • Take-away 3: Fragenkatalog aus Abschnitt 6 (Interaktivitätsanteil, geteilter State, SEO-Kritikalität, bestehende Investition) als konkret wiederverwendbares Werkzeug — tatsächlich anwenden, nicht nur Theorie
