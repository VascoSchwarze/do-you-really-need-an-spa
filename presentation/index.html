Ein kurzer Blick in die Vergangenheit...

Warum wurden SPAs zum Standard?

  • flüssigere UX
  • Nutzung von Hardware-Fortschritten
  • geringere Serverlast
  • klares mentales Modell
  • riesiges Ökosystem
  • Team-Gewohnheit
  • SPAs sind keine reine Modeerscheinung
  • flüssige, schnelle, responsive Navigation, App-ähnliches Gefühl
  • bessere Hardware in Endgeräten kann mehr Code selber ausführen
  • Rendering auf Client-Seite -> geringere Serverlast, weniger Netzwerkanfragen
  • klares mentales Modell: Komponentenwiederverwendung (gekapselte UI-Bausteine statt große HTML-Templates), klare Trennung von Frontend und Backend (einfachere Cross-Platform/mobile Anwendungen)
  • React/Vue/Angular-Ökosystem: ausgereiftes Tooling, riesige Community
  • nach Etablierung: Team-Gewohnheit: Weg des geringsten Widerstands, unabhängig von technischer Eignung, ich kenne das selbst
  • SPAs wurden auch zum Standard für reine Content-Seiten

Die technischen Kosten

  • JS benötigt
  • Größere Bundles
  • Verzögertes Laden der Seite
  • schwieriges SEO
  • Accessibility-Einschränkungen
  • ohne JS geht gar nichts
  • Bundlegröße skaliert schlecht, bspw, wenn ich neue Dependencies/Funktionalitäten auf einer Seite hinzufüge, wird dies immer mit geladen, auch wenn ich nur eine andere Seite sehen will
  • Reines CSR: Server liefert nur leeres HTML-Grundgerüst, sichtbarer Inhalt erst nach Download, Parsen und Ausführen des JS-Bundles (sequentiell) (auf schwachen Mobilgeräten besonders kritisch)
  • SEO
    • Google und zunehmend auch andere Suchmaschinen können SPAs crawlen/indexieren über zusätzlichen, Rendering-Schritt, klappt mittlerweise fast genauso gut wie MPAs
    • ABER: nicht jeder Bot rendert JS: Social-Preview-Bots (Slack, X, LinkedIn), Legacy-Tools sehen nur initiales HTML, welches leer ist
    • UND: einzelne Seiten können bei SPA nicht oder nur schwer unabhängig voneinander gerankt werden, aktualisierter Inhalt wird langsamer entdeckt/re-indexiert
  • Accessibility
    • Screenreader erkennen Seitenwechsel in SPAs oft nicht automatisch
    • Bestimmte Browser-integrierte Funktionen wie Formulare, Routing oder Historie müssen in SPAs oft nachgebaut und verwaltet werden
    • Mobile Daten kosten auch Geld, dann können mehrere MB für Nutzer teuer werden

Core Web Vitals

  • LCP   < 2,5sek
  • INP   < 200ms
  • CLS   < 0,1
  • Core Web Vitals = Google-definierte UX-Metriken, fließen in Suchranking ein (SEO)
  • LCP (Largest Contentful Paint): Ladezeitpunkt des größten Content-Element — bei CSR-SPAs abhängig von Bundle-Laden/Parsen/Ausführen + Datenladen, jede Stufe addiert sich (sollte unter 2,5 sek sein)
  • INP (Interaction to Next Paint): Reaktionsgeschwindigkeit auf Klicks/Eingaben — leidet bei blockiertem Hauptthread (sollte unter 200ms sein)
  • CLS (Cumulative Layout Shift): visuelle Stabilität, verschieben sich Elemente nach dem ersten Render? (sollte unter 0,1 sein)
  • Alle 3 Metriken: nicht nur UX-, sondern auch Business-relevant (SEO-Ranking)
  • TTI: nicht standardisiert, aber ehrlicher UX-Wert — wann Seite zuverlässig auf Eingaben reagiert (Event-Handler registriert, Hauptthread frei, keine Netzwerkaktivität)

Astros Philosophie

Ship Zero JavaScript by Default
  • Jede Astro-Komponente wird zu Build-/Request-Zeit zu statischem HTML/CSS gerendert, das dafür nötige JS wird verworfen
  • Umkehrung der SPA-Grundannahme: SPA = "alles braucht JS, bis Gegenteil bewiesen"; Astro = "nichts braucht JS, bis explizit als interaktiv markiert"
  • Dieser Perspektivwechsel ist der Kern der Islands Architecture (Details folgen)

Islands Architecture

Header (interaktive Insel)
Sidebar (statisch)
Hauptinhalt (statischer Text, Bilder etc.)
Karussell (interaktive Insel)
Footer (statisch)
  • JS wird nur für Inseln geladen
  • Laden inital zusammen mit dem Rest der Seite, oder auch erst, wenn das Element sichtbar wird

Ähnliche Content-first Ansätze

  • Qwik  -  Resumability
  • htmx  -  HTML-Attribute statt Komponenten
  • Next.js  -  Partial Prerendering / RSC
  • Astro  -  unser Beispiel heute
  • Einordnung für Kenner/Skeptiker ("ist das ein Astro-Werbe-Talk?"): Astro ist nicht die einzige/erste Umsetzung dieser Idee
  • Qwik: "Resumability" — serialisiert State ins HTML, setzt Ausführung im Client fort, ganz ohne Hydration-Schritt
  • htmx: kein Komponentenmodell, HTML-Attribute (hx-get/hx-post) laden Server-HTML-Fragmente nach, kein virtueller DOM
  • Next.js: Partial Prerendering / React Server Components — Server Components laufen nur serverseitig, nie client-seitiges JS
  • Astro als zugängliches Beispiel für größeres Denkmuster gewählt — nicht die einzig richtige Antwort

Anatomie einer .astro-Datei
  • .astro-Syntax ist Übermenge (engl. superset) von HTML, reines HTML ist gültige Astro-Komponente

Anatomie einer .astro-Datei
  • .astro-Datei hat zwei Zonen: "Frontmatter" oben zwischen drei Bindestrichen (enthält JS oder sogar TS), darunter das Template (HTML-artiges Markup)
  • Frontmatter: Ganz normales TypeScript: Imports, Typen, Props

Anatomie einer .astro-Datei
  • Inhalt von Frontmatter wird zur Build-Zeit ausgeführt (nie im Browser), es entsteht statisches HTML
  • Templatesyntax: Sieht aus wie JSX: {} betten JS-Ausdrücke ein, .map() für Listen funktioniert identisch
  • Kleine, aber angenehme Unterschiede zu JSX: normales class statt className, kein key-Prop bei Listen nötig
  • Kein umschließendes Fragment (<>...</>) nötig — ein Astro-Template darf mehrere Root-Elemente nebeneinander haben
  • Bedingtes Rendern wie in JSX: {condition && <div>...</div>}

Fazit

Interaktivität geht auch ohne Framework!

  • Wenn man möchte kann man React/Vue/Svelte/Solid/Preact-Komponenten als Islands einbinden, dann aber direkt wieder riesiges JS-Bundle was mitkommt
  • Echte Abwägung im Projekt: Bundle-Größe vs. Team-Vertrautheit/Entwicklungsgeschwindigkeit — bei komplexeren Features (z. B. Formulare) kann React-Insel pragmatischer sein
  • Punkt: nicht "Vanilla ist immer richtig", sondern bewusste Abwägung statt Reflex

Astro kann mehr als nur statisch

  • SSR
  • Server Islands
  • Actions
  • Endpoints
  • ...
  • Überleitung: "Zero JS by default" heißt nicht Verzicht auf dynamische Anforderungen
  • Hinzufügen eines Servers ermöglicht viele weitere Features

Serveradapter

astro.config.ts

  • Konzeptionell: Umstieg von output 'static' auf 'server'
  • Kein reiner Konfigurationsschalter: jetzt zwingend Deployment-(Server-)Adapter nötig (offiziell für Node, Vercel, Cloudflare, Netlify)

Serveradapter

astro.config.ts

  • Folge: reines statisches Hosting reicht nicht mehr — laufende Serverinstanz/Edge-Function nötig, Implikationen für Pipeline/Kosten/Skalierung
  • Umgesetzt in recipe-astro-server: output von 'static' auf 'server', dazu @astrojs/node als Adapter
  • mode: 'standalone' — der Adapter startet einen eigenständigen Node-Prozess, statt sich als Middleware in einen bestehenden Server einzuklinken
  • Ab jetzt sind Seiten standardmäßig on-demand (server-seitig gerendert), nicht mehr automatisch vorgerendert

Serveradapter

  • Wichtige Botschaft: output: 'server' heißt nicht "jetzt ist alles dynamisch" — pro Seite explizit wählbar
  • Rezept-Detailseiten, Übersicht, Startseite und Über-uns bleiben komplett vorgerendert, genau wie in recipe-astro
  • Nur die wirklich dynamischen Teile werden on-demand gerendert

Actions

  • Typisierte, serverseitige Funktionen
  • aufrufbar wie normale JS-Funktionen
  • Alternative zu einem rohen POST-Endpoint: Astro Actions kapseln Input-Validierung (Zod-Schema) und Server-Handler in einer typisierten Funktion
  • Im Beispielprojekt umgesetzt für die Rezept-Bewertung, statt eines separaten JSON-Endpoints

Actions

actions/index.ts

  • accept: 'form' erlaubt ein klassisches Formular als Input (FormData), nicht nur JSON
  • Zod-Schema validiert serverseitig, inkl. Typkonvertierung (z.coerce.number() aus dem Formular-String)
  • Handler läuft ausschließlich auf dem Server, Rückgabewert kommt typisiert beim Aufrufer an

Server Islands

  • dynamische, on-demand gerenderte Inseln

components/views/RecipeDetailView.astro

  • Konzeptionell: server:defer rendert eine Komponente weiter serverseitig, entkoppelt aber ihre Auslieferung vom Rest der Seite
  • Restliche Seite bleibt sofort verfügbar/schnell; Server-Island lädt asynchron nach, sobald fertig berechnet
  • Beispiel für unsere App: "gerade beliebte Rezepte" (zu häufig wechselnd für Build-Zeit-Rendering)
  • server:defer lässt Astro einen Platzhalter ins statische HTML rendern; die eigentliche Komponente wird per separatem Request nachgeladen, sobald die Seite im Browser aktiv ist
  • Dadurch bleiben TTFB/LCP der Hauptseite unabhängig davon, wie lange die Server-Insel für ihre Berechnung braucht

Server Islands

components/ServerHighlights.astro

  • Frontmatter von Server-Insel wird zur Laufzeit ausgeführt, statt zur Buildzeit, wie der Rest der Seite
  • Komponente holt sich ihre Daten selbst (eigener getCollection-Aufruf), typisch für Server Islands: eigenständige, an den Request gebundene Einheiten
  • recordView() erhöht den Zähler bei jedem Rendern, passiert also bei jedem Seitenaufruf neu, obwohl die restliche Seite vorgerendert/gecacht sein kann

SSR

  • komplette Seite on-demand gerendert
  • HTML-Templates mit dynamischem Code darin, der auf dem Server ausgeführt und zu HTML gerendert wird
  • "Herzlichen Glückwunsch, wir haben PHP neu erfunden"
  • keine reine Wiederholung, Islands sind gezielter/granularer als klassisches PHP-Rendering, aber die Grundrichtung "zurück zum Server" stimmt

SSR

pages/de/statistik.astro

  • export const prerender = false ist nicht unbedingt notwendig, da default output auf "server" gestellt wurde
  • Einzige Seite im Projekt, die explizit NICHT vorgerendert wird — läuft bei jedem Aufruf komplett neu auf dem Server
  • Zeigt Live-Zahlen (Gesamtaufrufe, meistgesehene Rezepte, letzte Bewertung) aus demselben In-Memory-Store wie der Server Island und die Action
  • Sinnvoll für Inhalte, die sich zu häufig ändern oder zu individuell sind, um vorab gebaut zu werden (Dashboards, personalisierte Seiten, Live-Daten)

Zwischenstand

  • Server Island — Live-Daten auf sonst vorgerenderter Seite
  • Astro Action — typisierter Aufruf eines Server-Endpunkts
  • On-Demand-Seite — komplett neu gerendert pro Request
  • Alle drei Features teilen sich einen einzigen In-Memory-Store (src/server/recipe-stats.ts) — bewusst keine Datenbank, um das Beispiel einfach und abhängigkeitsfrei zu halten
  • Der Rest der App (Content Collections, i18n, Client-Islands, gescoptes CSS) bleibt unverändert zu recipe-astro

Use Cases für Server-Funktionen

  • Authentifizierung & personalisierte Inhalte
  • CAPTCHAs
  • Häufig wechselnde, nicht vorab bekannte Daten
  • Reale Gründe für SSR/Server Islands: Auth (personalisierte Inhalte), CAPTCHAs (müssen serverseitig validiert werden), zu häufig/individuell wechselnde Inhalte (Dashboard, Warenkorb, Live-Preise)
  • Wichtige Botschaft: Wechsel zu "gezielt dynamisch" nur für die Teile, die es brauchen — nicht die ganze App
  • Vorteil ggü. "alles ist SPA": inkrementell genau so viel Dynamik hinzufügen wie nötig, hält ausgelieferten Code minimal

Wann SPAs die bessere Wahl sind

→ Komplexe, hochinteraktive Anwendungen mit viel Client-State

z.B. Dashboards, Editoren, Tools mit dauerhaftem "App-Charakter"

  • Astro und MPAs generell sind kein Wundermittel
  • SPAs bleiben beste Wahl für komplexe, hochinteraktive Apps mit viel geteiltem Client-State (Dashboards, Editoren, PM-Tools) — "App-Charakter" statt "Content-Charakter"
  • Keine Ausnahme von der Kernthese, sondern logische Konsequenz: bei interaktiven Tools ist "sehr viel JS" die ehrliche Antwort -> SPA ist dann konsequent richtig, keine schlechte Gewohnheit
  • Entwicklung komplexer JS-Logik ist mit einem Framework meist einfacher, als reines JS/TS zu schreiben

Ein Fragenkatalog

für euer nächstes Projekt

  1. Wie viel der Seite ist tatsächlich interaktiv vs. nur reiner Content?
  2. Wird clientseitiger Zustand benötigt, der über viele Komponenten hinweg geteilt und synchron gehalten werden muss?
  3. Ist SEO bzw. die Core Web Vitals ein kritischer Faktor?
  4. Besteht bereits eine erhebliche Investition in ein bestehendes SPA-Setup?
  • expliziter Fragenkatalog für jede Framework-Wahl, nicht Astro-spezifisch
  • Frage 1
    • Grundlegendste Frage: Marketing-Seite/Blog/Doku/Rezepte-App = überwiegend reiner Content → spricht für Islands-/Content-first-Ansatz
    • Grafik-Editor/PM-Board/Dashboard = fast alles interaktiv → klassische SPA passt besser
  • Frage 2
    • Anknüpfung an Favoriten-Toggle-Vergleich: braucht es geteilten, synchronen State über mehrere UI-Bereiche (z. B. Warenkorb-Icon, Formular mit Cross-Feld-Validierung)?
    • Islands sind bewusst isoliert — Stärke bei einfachen lokalen Interaktionen, Schwäche bei viel geteiltem State
    • Lösbar auch mit Islands (Astro empfiehlt Nanostores), aber ab gewissem Komplexitätsgrad ist SPA mit eingebautem State-Management oft pragmatischer
  • Frage 3
    • Öffentliche Inhalte (Marketing, Blog, Produktseiten, Doku): fast immer "ja" → spricht für Content-first-Ansatz
    • Interne Tools/Admin/Login-geschützt: SEO irrelevant → Argument entfällt, andere Kriterien entscheiden
  • Frage 4
    • Team-Know-how, gewachsene Codebasis, Tooling-Integrationen haben realen Wert/Umstellungskosten
    • Technisch "besseres" Paradigma rechtfertigt nicht automatisch Neuentwicklung
    • Abwägung: junges Projekt + starke Antworten auf Fragen 1-3 → Architektur-Vorteil überwiegt; etabliertes Produkt/eingespieltes Team → oft anders
  • Fragenkatalog ist bewusst tool-unabhängig formuliert
  • Wichtigste Botschaft: nicht ein Tool gegen ein anderes tauschen, sondern Entscheidungsprozess selbst bewusster gestalten

Die entscheidende Frage ist nicht "Welches Framework?", sondern "Wie viel JavaScript braucht diese Seite tatsächlich?"
